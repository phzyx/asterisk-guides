# 3. References and Locking

**Target tree:** Asterisk, the `24` branch. Line numbers and quoted code may
differ on newer releases and on other branches; re-grep for the symbol name if
you are reading against a different tree.

[Chapter 02](02-lifecycle.md) established who holds a reference to a channel and
what that keeps alive. This chapter is about the other half, and about the single
sentence from [the overview](README.md) that most needs paying off:

> A reference is not a lock. An ao2 reference guarantees the channel still exists;
> it says nothing about whether another thread is mutating it.

The two mechanisms are completely independent. They are spelled similarly, they
sit next to each other in `channel.h`, and they are both one-line wrappers over
ao2 — which is exactly why they get conflated.

```
   EXISTENCE                                 EXCLUSION
   ast_channel_ref / unref / cleanup         ast_channel_lock / unlock / trylock
   channel.h:3008 / :3019 / :3030            channel.h:2983 / :2984 / :2985
            │                                          │
            ▼                                          ▼
   ao2_ref(chan, ±1)                         ao2_lock(chan) → recursive mutex
            │                                          │
   "the memory will not be freed             "no other thread is inside a
    while I hold this"                        critical section on this channel"
            │                                          │
            └──────────────┬───────────────────────────┘
                           ▼
            Neither one tells you the channel is still
            usable: it may be a zombie, it may have been
            masqueraded out from under you, its name may
            have changed, its tech_pvt may now belong to
            a different device. See §3.2 and §3.8.
```

## 3.1 The two APIs

Both sets are macros, and both are thin:

```c
#define ast_channel_lock(chan) ao2_lock(chan)
#define ast_channel_unlock(chan) ao2_unlock(chan)
#define ast_channel_trylock(chan) ao2_trylock(chan)
```

`ast_channel_ref` and `ast_channel_unref` (`channel.h:3008`, `:3019`) are
`ao2_ref(c, +1)` and `ao2_ref(c, -1)` with a cast, and `ast_channel_cleanup`
(`:3030`) is `ao2_cleanup(c)`, which tolerates NULL. Nothing in any of them
touches the other mechanism.

What each one actually buys you:

| | A reference | The lock |
|---|---|---|
| The `struct ast_channel` memory stays mapped | yes | no |
| Field values stay stable while you read them | no | yes, for fields this thread does not itself mutate |
| String field pointers stay valid | no — see §3.2 | yes, for the duration of the critical section |
| The channel stays in the channel storage container | no | no |
| The channel is not hung up | no | no |
| The channel is not a zombie | no | no |
| Another thread can still be blocked in `ast_read` on it | yes | no |

The last row is the useful one for calibration. Holding a reference is compatible
with literally anything else happening. Holding the lock excludes other critical
sections and nothing more.

### The accessors do not lock

This is worth stating flatly because the accessor layer looks like an
encapsulation boundary and people reasonably expect encapsulated state to be
protected. It is not. Almost every getter in `main/channel_internal_api.c` is a
bare field read. The string field getters are generated by a macro whose entire
body is a return:

```c
#define DEFINE_STRINGFIELD_GETTER_FOR(field) const char *ast_channel_##field(const struct ast_channel *chan) \
{ \
	return chan->field; \
}
```

and the structural getters are the same shape by hand:

```c
struct ast_readq_list *ast_channel_readq(struct ast_channel *chan)
{
	return &chan->readq;
}
```

So `ast_channel_readq(chan)` hands you a pointer to a linked list head that
another thread may be splicing into. The accessor layer buys you ABI stability
and snapshot invalidation hooks (chapter 01), not thread safety. Locking is
entirely the caller's job, and the header says so in 22 places — 15 of them
spelled exactly `\pre chan is locked`, at `channel.h:1808`, `:2183`, `:2198`,
`:4198`, `:4288`, `:4339`, `:4357`, `:4362`, `:4398`, `:4411`, `:4435`, `:4967`,
`:4981`, `:4998` and `:5010`, plus one at `:5045` that goes further with
`\pre chan is locked  Absolutely _NO_ other channels can be locked.` The other
six are `\pre The chan and requestor channels are already locked` (`:1538`,
`:1552`), `\pre The channel needs to be locked` (`:2930`) and
`\note The channel must be locked when calling this function` (`:4898`, `:4910`,
`:4923`). 22 notes against roughly 490 prototypes is the real ratio: the
preconditions are documented where someone got burned, not systematically.

Two pairs of accessors are the exception, and they are instructive. Both
`ast_channel_unbridged` (`:886`) and `ast_channel_is_t38_active` (`:913`) take
the channel lock around the field read and each has a `_nolock` sibling
(`:881`, `:908`) for callers that already hold it; the matching setters
(`:901`, `:928`) lock too. So the accessor layer *can* lock when someone decides
it should — it just almost never does, and there is no way to tell which kind
you are calling except by reading it.

## 3.2 Why a reference is not enough: the string field hazard

The sharpest demonstration that a reference does not protect field *contents* is
`ast_channel_name`. It returns a `const char *` pointing into the channel's
string field pool. Setting a string field does not allocate a fresh buffer when
the new value fits in the old one — it overwrites the existing buffer in place:

```c
	if (*ptr != __ast_string_field_empty) {
		target = (char *) *ptr;
		available = AST_STRING_FIELD_ALLOCATION(*ptr);
		if (*ptr == mgr->last_alloc) {
			available += space;
		}
```

`target` is the pointer you are holding. A few lines later that target is handed
straight to `vsnprintf`. So a thread that renames a channel while you read
`ast_channel_name(chan)` without the lock can give you a torn string: the first
half of the new name and the tail of the old one, or a `NUL` in the middle.

It gets worse than torn. When a string field is released, the pool it lives in
can be freed outright if that field was the last live allocation in it:

```c
	for (pool = pool_head, prev = NULL; pool; prev = pool, pool = pool->prev) {
		if ((ptr >= pool->base) && (ptr <= (pool->base + pool->size))) {
			pool->active -= AST_STRING_FIELD_ALLOCATION(ptr);
			if (pool->active == 0) {
				if (prev) {
					prev->prev = pool->prev;
					ast_free(pool);
				} else {
					pool->used = 0;
				}
			}
			break;
		}
	}
```

`ast_free(pool)` is a real free during the channel's lifetime, not just at
destruction. Your `const char *` can become a dangling pointer into freed memory
while your ao2 reference on the channel remains perfectly valid. The reference
protects the `struct ast_channel`; it does not protect the pools hanging off it.

And renames are not exotic. Masquerade changes both channels' names as a matter
of course — `channel_do_masquerade` unlinks them from channel storage precisely
because the name is a container key (`channel.c:6922-6934`, quoted in §3.6).

Three correct ways to read a channel's name:

1. Lock the channel, `ast_strdupa`/`ast_copy_string` it into your own buffer,
   unlock. This is the dominant idiom in the tree.
2. Take a snapshot — `ast_channel_snapshot_get_latest(uniqueid)`
   (`stasis_channels.h:252`) — and read the snapshot's copy. The snapshot is an
   immutable ao2 object; your reference to it is a complete guarantee. This is
   what the AMI, ARI, CDR and CEL consumers do, and it is the only lock-free
   read in the system that is actually safe.
3. Hold the lock across the whole use. Fine for a `ast_log` call, wrong if you
   are about to do anything that blocks (§3.4).

What is *not* correct is the very common-looking

<!-- illustrative -->
```c
/* WRONG */
const char *name = ast_channel_name(chan);   /* no lock held */
do_something_slow();
ast_log(LOG_NOTICE, "channel %s\n", name);
```

## 3.3 What the lock actually is

`ast_channel_lock` is `ao2_lock`, which is `__ao2_lock(a, AO2_LOCK_REQ_MUTEX, ...)`
(`astobj2.h:717`). Channels are allocated with `AO2_ALLOC_OPT_LOCK_MUTEX`, so the
dispatch inside `__ao2_lock` lands here:

```c
	switch (obj->priv_data.options & AO2_ALLOC_OPT_LOCK_MASK) {
	case AO2_ALLOC_OPT_LOCK_MUTEX:
		obj_mutex = INTERNAL_OBJ_MUTEX(user_data);
		res = __ast_pthread_mutex_lock(file, line, func, var, &obj_mutex->mutex.lock);
```

and `__ast_pthread_mutex_lock` operates on a mutex initialised with
`AST_MUTEX_KIND`:

```c
	pthread_mutexattr_init(&attr);
	pthread_mutexattr_settype(&attr, AST_MUTEX_KIND);
	res = pthread_mutex_init(&t->mutex, &attr);
	pthread_mutexattr_destroy(&attr);
```

`AST_MUTEX_KIND` is `PTHREAD_MUTEX_RECURSIVE_NP` or `PTHREAD_MUTEX_RECURSIVE`,
and the header is unambiguous that there is no build configuration in which it is
anything else:

```c
/* Asterisk REQUIRES recursive (not error checking) mutexes
   and will not run without them. */
#if defined(HAVE_PTHREAD_RECURSIVE_MUTEX_INITIALIZER_NP) && defined(HAVE_PTHREAD_MUTEX_RECURSIVE_NP)
#define PTHREAD_MUTEX_INIT_VALUE	PTHREAD_RECURSIVE_MUTEX_INITIALIZER_NP
#define AST_MUTEX_KIND			PTHREAD_MUTEX_RECURSIVE_NP
#else
#define PTHREAD_MUTEX_INIT_VALUE	PTHREAD_MUTEX_INITIALIZER
#define AST_MUTEX_KIND			PTHREAD_MUTEX_RECURSIVE
#endif /* PTHREAD_RECURSIVE_MUTEX_INITIALIZER_NP */
```

### The recursion is load-bearing

It would be easy to read "recursive" as defensive sloppiness. It is not — the
core depends on it. `ast_channel_setwhentohangup_tv` is documented as requiring
the lock:

```c
 * This function sets the absolute time out on a channel (when to hang up).
 *
 * \pre chan is locked
 *
 * \since 1.6.1
 */
void ast_channel_setwhentohangup_tv(struct ast_channel *chan, struct timeval offset);
```

and its body queues a frame:

```c
void ast_channel_setwhentohangup_tv(struct ast_channel *chan, struct timeval offset)
{
	if (ast_tvzero(offset)) {
		ast_channel_whentohangup_set(chan, &offset);
	} else {
		struct timeval tv = ast_tvadd(offset, ast_tvnow());
		ast_channel_whentohangup_set(chan, &tv);
	}
	ast_queue_frame(chan, &ast_null_frame);
	return;
}
```

while `ast_queue_frame` funnels into `__ast_queue_frame`, which takes the channel
lock itself:

```c
static int __ast_queue_frame(struct ast_channel *chan, struct ast_frame *fin, int head, struct ast_frame *after)
{
	struct ast_frame *f;
	struct ast_frame *cur;
	unsigned int new_frames = 0;
	unsigned int new_voice_frames = 0;
	unsigned int queued_frames = 0;
	unsigned int queued_voice_frames = 0;
	AST_LIST_HEAD_NOLOCK(,ast_frame) frames;

	ast_channel_lock(chan);
```

So the documented call sequence acquires the channel lock twice in one thread.
With a non-recursive mutex, setting a channel's hangup time would self-deadlock.
This pattern — a lock-requiring function calling a self-locking one — recurs
throughout `channel.c`, and it is why
[chapter 02](02-lifecycle.md) is careful to say the channel's mutex is recursive
unconditionally rather than only under `DEBUG_THREADS`.

The practical consequence for your own code: `ast_channel_lock` succeeding tells
you nothing about whether *this* thread already held it. If you need to know, you
have to track it yourself.

### Nobody checks the return value

`ao2_lock` returns `int`, and `ast_channel_lock` inherits it. Of the 797 textual
occurrences of `ast_channel_lock(` across the `.c` and `.h` files in the tree,
**zero** appear in an `if`, an assignment, or under a `!`. The return is
universally discarded. `ast_channel_trylock` is the opposite — of its 35 occurrences, 33 sit inside an
`if` or a `while` condition, and the remaining two are the macro definition
itself and a prototype in the standalone `utils/extconf.c`. Every actual call
tests the result, because that is the entire point of it.

A lock failure on a channel is therefore silent. In practice the only ways
`__ao2_lock` fails are a NULL object or a corrupted ao2 header, both of which are
already fatal classes of bug, so this is defensible; it is still worth knowing
that the code has no opinion about it.

## 3.4 What the lock protects, and what it does not

The channel lock is a single mutex guarding a ~113-field struct, so "what it
protects" is best stated as a boundary rather than a list.

**Inside the boundary.** The read queue, the flag word, the datastore list, the
fd vector and alert pipe, the party structures (caller, connected, redirecting,
dialed), the formats and stream topology, `whentohangup`, the softhangup bits,
the generator state, the masq/masqr pointers, and the string fields. Mutating any
of these without the lock is a bug even if it looks atomic — `ast_set_flag` is a
read-modify-write on a bitfield shared with other flags.

**Outside the boundary, three important cases.**

*The tech pvt.* `ast_channel_tech_pvt(chan)` returns the driver's private
structure. The channel lock protects the *pointer*; the contents are the driver's
problem and almost every driver has its own mutex for them. The documented order
is channel first, then pvt (`lock.h:412-414`), and §3.8 is largely about what
happens when a driver needs them the other way round.

*Container membership.* Whether the channel is in channel storage is container
state, protected by the container's lock, not the channel's. You can hold a
channel's lock while it is unlinked beneath you.

*Blocking.* The lock does not make it safe to block. If you hold the channel lock
and then call something that waits — a read, a poll, a `usleep`, a taskprocessor
push that might queue — you have serialised every other thread that wants that
channel, including the one trying to hang it up. `CHECK_BLOCKING` exists to catch
the specific case of two threads both trying to wait on a channel's media, and it
has its own precondition:

```c
 * Masquerading and ast_queue_frame() use this indication to wake up the thread.
 *
 * \pre The channel needs to be locked
 */
#define CHECK_BLOCKING(c) \
	do { \
		if (ast_test_flag(ast_channel_flags(c), AST_FLAG_BLOCKING)) { \
			/* This should not happen as there should only be one thread handling a channel's media at a time. */ \
			ast_log(LOG_DEBUG, "Thread LWP %d is blocking '%s', already blocked by thread LWP %d in procedure %s\n", \
				ast_get_tid(), ast_channel_name(c), \
				ast_channel_blocker_tid(c), ast_channel_blockproc(c)); \
			ast_assert(0); \
		} \
		ast_channel_blocker_tid_set((c), ast_get_tid()); \
		ast_channel_blocker_set((c), pthread_self()); \
		ast_channel_blockproc_set((c), __PRETTY_FUNCTION__); \
		ast_set_flag(ast_channel_flags(c), AST_FLAG_BLOCKING); \
	} while (0)
```

Note what this implies: the *flag* is set under the lock, but the blocking
operation itself then happens with the lock released. That is the shape all
blocking work on a channel has to take.

## 3.5 Scoped locking

`SCOPED_CHANNELLOCK` is the RAII form, used at 33 sites:

```c
#define SCOPED_CHANNELLOCK(varname, chan) SCOPED_LOCK(varname, (chan), ast_channel_lock, ast_channel_unlock)
```

which expands through

```c
#define SCOPED_LOCK(varname, lock, lockfunc, unlockfunc) \
	RAII_VAR(typeof((lock)), varname, ({lockfunc((lock)); (lock); }), unlockfunc)
```

to a `RAII_VAR`, of which there are 2,725 uses in the tree. `RAII_VAR` relies on
GCC's `__attribute__((cleanup))` — the unlock runs when the variable goes out of
scope, including on an early `return` or a `goto` that leaves the block.

Two things to know before reaching for it:

- **You cannot unlock early.** The unlock is tied to scope exit, so any function
  that needs to drop the channel lock in the middle — which is most functions
  that do anything interesting, see §3.4 on blocking — cannot use this. Opening
  an inner block just to scope the lock works but reads poorly.
- **It composes badly with deadlock avoidance.** The macros in §3.8 unlock and
  relock the same lock; doing that to a scoped lock is legal but means the
  cleanup handler may be unlocking a lock a different acquisition obtained, which
  defeats the lock-site tracking those macros exist to preserve.

The manual `ast_channel_lock` / `ast_channel_unlock` pair outnumbers the scoped
form by more than twenty to one, and that ratio is not an accident.

## 3.6 Lock ordering

Asterisk has no global lock hierarchy and no runtime ordering check. What it has
is a set of orderings documented in the headers of the subsystems that care. The
four that matter for channels:

**Channel storage container, then channel.** Stated as a prohibition in the
masquerade comment:

```c
/*!
 * \brief Masquerade a channel
 *
 * \note Assumes _NO_ channels and _NO_ channel pvt's are locked.  If a channel is locked while calling
 *       this function, it invalidates our channel container locking order.  All channels
 *       must be unlocked before it is permissible to lock the channels' ao2 container.
 */
```

The container-then-channel direction is exercised on every lookup. `ao2_callback`
holds the container lock while it runs the comparison callback, and the callback
locks each candidate channel:

```c
static int by_name_cb(void *obj, void *arg, void *data, int flags)
{
	struct ast_channel *chan = obj;
	const char *name = arg;
	size_t name_len = *(size_t *) data;
	int ret = 0;

	ast_channel_lock(chan);
	if (name_len == 0) {
		if(strcasecmp(ast_channel_name(chan), name) == 0) {
			ret = CMP_MATCH | ((flags & OBJ_MULTIPLE) ? 0 : CMP_STOP);
		}
	} else {
		if (strncasecmp(ast_channel_name(chan), name, name_len) == 0) {
			ret = CMP_MATCH | ((flags & OBJ_MULTIPLE) ? 0 : CMP_STOP);
		}
	}
	ast_channel_unlock(chan);

	return ret;
}
```

That is container → channel, in-order and safe. The reverse — holding a channel
lock and then calling a search function — is what the masquerade comment forbids,
and what the header warns about over the entire search API:

```c
/*!
* \warning Absolutely _NO_ channel locks should be held while calling any of
* these functions.
*/
```

The same prohibition appears as `\note Absolutely _NO_ channel locks should be
held before calling this function` on 13 individual declarations in `channel.h`,
among them `__ast_channel_alloc` (note at `:1253`, named at `:1259`),
`ast_channel_release` (`:1479` / `:1483`), `ast_hangup` (`:1632` / `:1638`) and
`ast_set_hangupsource` (`:1689` / `:1697`).

**Bridge, then bridge channel, then channel** (`bridge_channel.h:33-38`):

```c
 * In general, anywhere else it is unsafe to use this API. Care should be
 * taken when using this API to ensure that the locking order remains
 * correct. The locking order must be:
 *  \arg The \ref ast_bridge "\c ast_bridge"
 *  \arg The \ref ast_bridge_channel "\c ast_bridge_channel"
 *  \arg The \ref ast_channel "\c ast_channel"
```

Chapter 02's note that a bridge holds a *borrowed* `bridge_channel->chan` pointer
rather than a reference is the lifetime half of this; the ordering above is the
exclusion half. Both have to hold.

**Channel, then tech pvt** (`lock.h:412-414`, in the `DLA_UNLOCK` documentation):
"the locking order specifies that we may safely lock a channel, followed by its
pvt, with no worries about a deadlock."

**Channel, then autochan.** `struct ast_autochan` exists so that a module holding
onto a channel across a masquerade follows the swap. Its locking macro is the
cleanest worked example of ordering-by-trylock in the tree:

```c
/*!
 * \brief Lock the autochan's channel lock.
 *
 * \note We must do deadlock avoidance because the channel lock is
 * superior to the autochan lock in locking order.
 */
#define ast_autochan_channel_lock(autochan) \
	do { \
		ast_mutex_lock(&(autochan)->lock); \
		while (ast_channel_trylock((autochan)->chan)) { \
			DEADLOCK_AVOIDANCE(&(autochan)->lock); \
		} \
		ast_mutex_unlock(&(autochan)->lock); \
	} while (0)
```

Read that carefully, because it is doing something subtle. The autochan lock is
*inferior* to the channel lock, so this code — which must consult
`autochan->chan` under the autochan lock before it can lock the channel — is
structurally in the wrong order. It resolves this by never *waiting* out of
order: it trylocks the channel, and on failure drops the autochan lock entirely
(via `DEADLOCK_AVOIDANCE`) before trying again. And the header's own usage notes
spell out why the dance is necessary at all (`autochan.h:56-59`): saving off
`autochan->chan` requires `ast_channel_ref`, because a masquerade can otherwise
invalidate the saved pointer — reference and lock, each solving its own half.

### The container lock is not a reader/writer lock

The channel storage API exposes `rdlock` and `wrlock` separately
(`channelstorage.h:51-52`), which suggests shared reads. For the default
`ao2_legacy` driver they are the same function:

```c
static struct ast_channelstorage_instance channelstorage_instance = {
	.handle = NULL,
	.close_instance = close_instance,
	.insert = insert_channel,
	.remove = delete_channel,
	.rdlock = lock_driver,
	.wrlock = lock_driver,
	.unlock = unlock_driver,
```

pointing at

```c
static void lock_driver(struct ast_channelstorage_instance *driver)
{
	ao2_lock(getdb(driver));
}

static void unlock_driver(struct ast_channelstorage_instance *driver)
{
	ao2_unlock(getdb(driver));
}
```

and the container itself is allocated `AO2_ALLOC_OPT_LOCK_MUTEX`
(`channelstorage_ao2_legacy.c:372-373`). So every "read lock" on channel storage
is exclusive. Code that takes the container lock and then does something slow
stalls every channel lookup in the process. Masquerade does exactly this, by
necessity, holding the write lock across the rename:

```c
	/*
	 * The container lock is necessary for proper locking order
	 * because the channels must be unlinked to change their
	 * names.
	 *
	 * The original and clonechan locks must be held while the
	 * channel contents are shuffled around for the masquerade.
	 *
	 * The masq and masqr pointers need to be left alone until the masquerade
	 * has restabilized the channels to hold off ast_hangup() and until
	 * AST_FLAG_ZOMBIE can be set on the clonechan.
	 */
	CHANNELSTORAGE_API(current_channel_storage_instance, wrlock);
```

Iterators are the exception: `ast_channel_iterator_next` (`channel.h:3131`) wraps
`ao2_iterator_next`, which takes and releases the container lock once per step.
An iterator does not hold the container lock between steps, which is why it is
safe to lock a channel you got from one — and also why the set of channels you
walk is not a consistent snapshot.

## 3.7 Two channels at once

There is no ordering defined between two channels. They are peer objects in the
same container with no hierarchy, so the only safe way to hold both locks is to
take one and *try* for the other:

```c
#define ast_channel_lock_both(chan1, chan2) do { \
		ast_channel_lock(chan1); \
		while (ast_channel_trylock(chan2)) { \
			ast_channel_unlock(chan1); \
			sched_yield(); \
			ast_channel_lock(chan1); \
		} \
	} while (0)
```

42 call sites use this. The `sched_yield()` rather than `usleep(1)` is the only
difference from the deadlock-avoidance macros below.

The trap is in what this macro does *not* promise. It is not atomic. Inside the
retry loop `chan1` is unlocked, and on the next iteration it is reacquired — so
everything you knew about `chan1` before calling `ast_channel_lock_both` may be
false after it returns. If you validated `chan1`'s state, or cached a pointer out
of it, you must revalidate. The macro's own name encourages exactly the wrong
mental model: it reads like an atomic two-lock acquisition and it is not.

For three or more channels there is no macro, and the tree's answer is to
restructure so you do not need three.

## 3.8 Deadlock avoidance

When a thread holds lock A and needs lock B, and some other thread in the system
acquires them in the other order, somebody has to give way. Asterisk's answer is
a family of macros that drop the lock you hold, sleep a microsecond, and take it
back — then require you to revalidate everything.

`CHANNEL_DEADLOCK_AVOIDANCE` has two definitions. Without `DEBUG_THREADS` it is
exactly what it says:

```c
#define CHANNEL_DEADLOCK_AVOIDANCE(chan) \
	ast_channel_unlock(chan); \
	usleep(1); \
	ast_channel_lock(chan);
```

Note that this version is **not** wrapped in `do { } while (0)`. It expands to
three statements, so `if (cond) CHANNEL_DEADLOCK_AVOIDANCE(chan);` makes only the
unlock conditional and then unconditionally sleeps and relocks. All five call
sites in the tree happen to use braces, so this has never bitten anyone, but it
is a live trap for new code.

Under `DEBUG_THREADS` the macro becomes substantial, because the whole point of
the debug build is that `core show locks` can tell you where a lock was acquired
— and a naive unlock/relock would relabel the lock as having been acquired inside
the macro. So it captures the original site first:

```c
#define CHANNEL_DEADLOCK_AVOIDANCE(chan) \
	do { \
		char __filename[80], __func[80], __mutex_name[80]; \
		int __lineno; \
		int __res = ast_find_lock_info(ao2_object_get_lockaddr(chan), __filename, sizeof(__filename), &__lineno, __func, sizeof(__func), __mutex_name, sizeof(__mutex_name)); \
		int __res2 = ast_channel_unlock(chan); \
		usleep(1); \
		if (__res < 0) { /* Shouldn't ever happen, but just in case... */ \
			if (__res2) { \
				ast_log(LOG_WARNING, "Could not unlock channel '%s': %s and no lock info found!  I will NOT try to relock.\n", #chan, strerror(__res2)); \
			} else { \
				ast_channel_lock(chan); \
			} \
		} else { \
			if (__res2) { \
				ast_log(LOG_WARNING, "Could not unlock channel '%s': %s.  {{{Originally locked at %s line %d: (%s) '%s'}}}  I will NOT try to relock.\n", #chan, strerror(__res2), __filename, __lineno, __func, __mutex_name); \
			} else { \
				__ao2_lock(chan, AO2_LOCK_REQ_MUTEX, __filename, __func, __lineno, __mutex_name); \
			} \
		} \
	} while (0)
```

`ast_find_lock_info` (`lock.h:331`) retrieves the recorded acquisition site, and
the relock goes through `__ao2_lock` with that site passed back in explicitly
rather than through `ast_channel_lock`, which would record the macro's own
location. The `__res2` branches exist because an unlock can fail — if it does,
the macro logs loudly and deliberately does *not* relock, on the grounds that a
failed unlock means the lock state is already not what the caller believes.

There are only five call sites for `CHANNEL_DEADLOCK_AVOIDANCE` in the entire
tree: `main/channel.c:2555`, `channels/chan_dahdi.c:8098` and `:8865`, and
`addons/chan_mobile.c:1119` and `:1180`. `AO2_DEADLOCK_AVOIDANCE` has exactly one
(`main/stasis.c:496`). This is not a routine tool.

### The core's own use: waiting out a masquerade

`ast_hangup` cannot proceed while a masquerade is pending on the channel, and it
cannot hold the channel lock while waiting, because the masquerade needs it:

```c
	ast_channel_lock(chan);

	while (ast_channel_masq(chan) || ast_channel_masqr(chan))  {
		CHANNEL_DEADLOCK_AVOIDANCE(chan);
	}
```

The loop re-tests the condition after each relock, which is the correct shape:
the macro gives up the lock, so the predicate has to be rechecked, not assumed.

### The canonical driver pattern, and the revalidation it requires

`dahdi_read` is called by the core with the channel already locked, and needs the
pvt lock. That is the documented order — channel then pvt — yet it still cannot
simply block on the pvt lock, because the driver's own threads reach the channel
through the pvt:

```c
	/*
	 * For analog channels, we must do deadlock avoidance because
	 * analog ports can have more than one Asterisk channel using
	 * the same private structure.
	 */
	p = ast_channel_tech_pvt(ast);
	while (ast_mutex_trylock(&p->lock)) {
		CHANNEL_DEADLOCK_AVOIDANCE(ast);

		/*
		 * Check to see if the channel is still associated with the same
		 * private structure.  While the Asterisk channel was unlocked
		 * the following events may have occurred:
		 *
		 * 1) A masquerade may have associated the channel with another
		 * technology or private structure.
		 *
		 * 2) For PRI calls, call signaling could change the channel
		 * association to another B channel (private structure).
		 */
		if (ast_channel_tech_pvt(ast) != p) {
			/* The channel is no longer associated.  Quit gracefully. */
			return &ast_null_frame;
		}
	}
```

The comment at `:8867-8877` is the most valuable thing in this chapter. After
`CHANNEL_DEADLOCK_AVOIDANCE` releases and reacquires the channel lock, the
channel may no longer be the same channel in any meaningful sense: a masquerade
may have swapped its tech and pvt, or PRI signalling may have moved it to a
different B channel. So the loop body ends by rechecking
`ast_channel_tech_pvt(ast) != p` and bailing out if the association is gone.

Every use of deadlock avoidance needs an equivalent recheck. The macro is not
"briefly yield the lock" — it is "abandon every assumption you had and start
over."

### `DLA_UNLOCK` / `DLA_LOCK`

When a thread holds *two* locks and needs to drop both, the lock-site
preservation has to span both unlocks. `DLA_UNLOCK` (`lock.h:417`) and `DLA_LOCK`
(`:436`) are the split form of `DEADLOCK_AVOIDANCE`: literally one
`do { ... } while (0)` cut in half, with the declarations and the unlock in the
first macro and the relock and error handling in the second, so the `do {` opened
at `:418` is closed by the `} while (0)` at `:450` inside the *other* macro. They
must therefore be used as a pair, in the same scope, with the other avoidance
macro nested between them. (Without `DEBUG_THREADS` they collapse to a plain
`ast_mutex_unlock` and `ast_mutex_lock`, `:497` and `:499` — no sleep, no
tracking, and no `do`/`while` to balance.) Only one place in the tree uses them —
the DAHDI three-way-call path, which holds the pvt lock and the main channel's
lock and needs a second channel's lock:

```c
					/* Here we have to retain the lock on both the main channel, the 3-way channel, and
					   the private structure -- not especially easy or clean */
					while (p->subs[SUB_THREEWAY].owner && ast_channel_trylock(p->subs[SUB_THREEWAY].owner)) {
						/* Yuck, didn't get the lock on the 3-way, gotta release everything and re-grab! */
						DLA_UNLOCK(&p->lock);
						CHANNEL_DEADLOCK_AVOIDANCE(ast);
						/* We can grab ast and p in that order, without worry.  We should make sure
						   nothing seriously bad has happened though like some sort of bizarre double
						   masquerade! */
						DLA_LOCK(&p->lock);
						if (p->owner != ast) {
							ast_log(LOG_WARNING, "This isn't good...\n");
							return NULL;
						}
```

Note the revalidation again at `:8103`, and that the two channels here have no
defined order between them, which is why trylock is the only option.

## 3.9 Debugging

Lock problems in Asterisk are diagnosed almost entirely through two compile-time
options in `menuselect`: `DEBUG_THREADS`, under *Compiler Flags*
(`build_tools/cflags.xml:12`), and `DETECT_DEADLOCKS`, under *Compiler Flags -
Development* (`build_tools/cflags-devmode.xml:11`), which only appears in an
`--enable-dev-mode` build.

`DEBUG_THREADS` — or `DETECT_DEADLOCKS`, which activates the same machinery —
turns on a lazily allocated `struct ast_lock_track *` on every `ast_mutex_t` and
`ast_rwlock_t`, recording file, line, function and thread for each nesting level,
up to `AST_MAX_REENTRANCY` (10, `lock.h:108`), and registers a per-thread list of
held locks. The pointer field exists in every build; without either flag it is
renamed `_track` so it cannot be touched (`lock.h:142-157` for the mutex,
`:164-179` for the rwlock), and the header is explicit that "we have tracking
information in this structure regardless of DEBUG_THREADS being enabled"
(`lock.h:139`):

| Symbol | Where | Meaning |
|---|---|---|
| `struct thr_lock_info` | `utils.c:996-1031` | one per thread; the array of locks it holds, plus `pending` and `suspended` bits |
| `struct ast_lock_track` | `lock.h:118-128` | per lock; the acquisition site at each of up to 10 nesting levels |
| `AST_MAX_LOCKS` | `utils.c:982` | 64 locks tracked per thread; exceeding it logs "Increase AST_MAX_LOCKS!" |
| `AST_MAX_REENTRANCY` | `lock.h:108` | 10 nesting levels tracked per lock |
| `ast_store_lock_info` | `utils.c:1088` | called from every lock acquisition |
| `ast_find_lock_info` | `lock.h:331` | what the avoidance macros use to preserve the original site |
| `ast_dump_locks` | `lock.h:323` | the `ast_str` behind the CLI command |
| `core show locks` | `utils.c:1558` | the CLI command itself |

`core show locks` is the first thing to run on a wedged Asterisk. It prints, per
thread, the stack of locks held and the one it is waiting on; a cycle across two
threads is a deadlock and the two lock-acquisition sites it names are the bug.
With `HAVE_BKTR` it also prints a backtrace per acquisition.

`DETECT_DEADLOCKS` is the more aggressive option: it replaces the blocking
`pthread_mutex_lock` with a trylock loop that logs every five seconds and emits
an AMI `DeadlockStart` event (`lock.c:288-350`, the log at `:303`):

```
%s line %d (%s): Deadlock? waited %d sec for mutex '%s'?
```

followed, if `DEBUG_THREADS` is also on, by where that mutex was locked. The
event is emitted only once per episode, guarded by `if ((int) wait_time < 10)` at
`lock.c:321` — a deliberate choice so that a long deadlock does not flood AMI.

Both options cost real performance and neither belongs in production. The
`ast_channel_lock` call sites do not change; only what happens underneath them
does.

## 3.10 Common bugs

| Symptom | Cause |
|---|---|
| Garbled or truncated channel name in a log line | read a string field getter without the lock; §3.2 |
| Use-after-free on a `const char *` from a channel | same, with the pool freed by `__ast_string_field_release_active` |
| Deadlock with one thread in `ao2_callback` and one in `ast_channel_lock` | called a search function while holding a channel lock; `channel.h:3137` |
| Deadlock between a driver thread and the PBX thread | driver took its pvt lock then the channel lock, reversing `lock.h:412-414` |
| Intermittent crash in a driver's `read`/`write` after a transfer | used deadlock avoidance without revalidating; `chan_dahdi.c:8878` is the model |
| Stale state after `ast_channel_lock_both` | treated it as atomic; `chan1` is unlocked inside its retry loop |
| Everything stalls during a transfer or rename | something slow ran while holding the channel storage lock, which is exclusive even for "reads" |
| Self-deadlock that only appears on one platform | relied on the mutex *not* being recursive, or hand-rolled a `pthread_mutex_t`; `lock.h:80-81` |
| `ast_assert` fires in `CHECK_BLOCKING` | two threads are both trying to wait on one channel's media |

## 3.11 Rules

| Rule | Why |
|---|---|
| Get the reference first, then the lock, in that order | locking an object you do not have a reference to is a race against its destructor |
| Never hold a channel lock across anything that blocks | you serialise every thread that wants the channel, including the hangup path |
| Copy string fields out under the lock; never cache the pointer | the buffer is overwritten in place and its pool can be freed |
| Prefer a snapshot for read-only access from outside the channel's own thread | immutable, ao2-refcounted, needs no channel lock at all |
| Never call a channel search or lookup function with a channel lock held | inverts container → channel |
| Use `ast_channel_lock_both` for two channels, and revalidate after it returns | there is no order between peer channels, and the macro is not atomic |
| After any deadlock-avoidance macro, recheck every predicate and every cached pointer | the channel may have been masqueraded, renamed or reassigned |
| Brace every `CHANNEL_DEADLOCK_AVOIDANCE` | the non-debug expansion is three bare statements |
| Reach for deadlock avoidance last | five call sites in the whole tree; if you need a sixth, the ordering is probably wrong |
| Reproduce lock bugs with `DEBUG_THREADS` and read `core show locks` | it names both acquisition sites, which is the whole answer |
